Architecture

When real-time systems need to be boring

Explicit state transitions make live AI workflows easier to test, recover, and explain.

Written by
Montasim Shuvo
Published August 18, 2026
Reading time 12 minutes
On this page Introduction Transitions Recovery Discussion

Introduction

Real-time products feel alive because several things happen at once. A user speaks, a model responds, tools run, and the interface updates before the whole operation is finished. The implementation gets easier to trust when those events pass through a small set of explicit states.

The goal is not to make the experience feel mechanical. The goal is to make the machinery predictable enough that the experience can feel fluid.

Start with transitions, not flags

A collection of booleans can describe many impossible combinations. An explicit state model limits the system to situations that can actually occur. That gives every event a clear starting point, destination, and owner.

If a transition cannot be named, the system probably does not know who owns it.

Idle, listening, thinking, speaking, and recovering are useful because they describe what the product is doing. They also make cleanup visible. Leaving a state becomes the natural place to stop audio, cancel a timeout, or detach a listener.

Recovery is part of the normal path

Networks stall. Browsers suspend tabs. People interrupt. Treating recovery as a first-class transition keeps these ordinary events from becoming mysterious edge cases.

The result is intentionally boring code: one event enters, one transition is selected, and one set of effects follows. That boredom buys a calmer product for the person using it.
