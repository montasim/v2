### Routempo

- **Repository / revision:** [montasim/Routempo](https://github.com/montasim/Routempo), default branch `main`, HEAD `40ad55a0205d85f1b70b0c46d712ff8db6742377`. Primary evidence: [README](https://github.com/montasim/Routempo/blob/40ad55a0205d85f1b70b0c46d712ff8db6742377/README.md), [package manifest](https://github.com/montasim/Routempo/blob/40ad55a0205d85f1b70b0c46d712ff8db6742377/package.json), [source tree](https://github.com/montasim/Routempo/tree/40ad55a0205d85f1b70b0c46d712ff8db6742377/src), and [data-layer ADR](https://github.com/montasim/Routempo/blob/40ad55a0205d85f1b70b0c46d712ff8db6742377/docs/research/neon-data-layer.md).
- **Role / scope / status:** Maintainer-built, full-stack routine-planning product covering planning, completion logging, review, calendar/task connections, reminders, data portability, authentication, persistence, and automated tests. The README describes an active application while documenting privacy and operational limitations; no employment or multi-person team claim is supported.
- **Problem:** Repeatable routines are easy to schedule but hard to evaluate when plans, actual outcomes, timezone changes, and external calendars live in separate systems.
- **Constraints:** (1) schedule and completion semantics must remain correct across user timezones; (2) reminders require browser permission, subscriptions, and a scheduled server invocation; (3) OAuth integrations depend on provider scopes and configuration, while exported/imported personal data must preserve user control.
- **Architecture (4 layers):** TanStack Start routes and React UI; routine/session/review domain services; Drizzle repositories over Neon PostgreSQL plus Better Auth; Web Push and Google Calendar/Tasks adapters with scheduled summary endpoints.
- **Technical decisions:** (1) Store durable behavioral records in PostgreSQL through Drizzle rather than browser-only state, trading infrastructure for queryable history and portability; (2) separate planned routines from recorded outcomes so analysis reflects actual behavior; (3) isolate notification and OAuth integrations behind configured boundaries so the core planner remains usable without every external connection.
- **Concrete contributions:** Built repeatable routine creation and daily execution flows; modeled sessions, check-ins, reviews, and account data in migrations/schema; added calendar/task sync, push subscriptions, scheduled weekly summaries, import/export, and deletion paths; established Vitest, Testing Library, and Playwright coverage.
- **Outcomes / capabilities:** Users can plan and run routines; record outcomes and review patterns; move account data in and out; optionally connect Google services and receive reminders/summaries. These are capabilities, not adoption or productivity metrics.
- **Screenshot relevance:** The portfolio image is relevant if it shows the planner, execution state, or review surface. The repository has prototype and design-system material but the README does not identify a canonical production screenshot, so do not present a generic mockup as verified live proof.
